# 테스트 원칙과 감사 기록 (UI 쪽: ui · controllers/unit_actions · tool/capture)

기준은 데이터 쪽과 같다(`docs/testing.md`): Khorikov 4기둥(회귀 보호 · 리팩터링 내성 · 빠른 피드백 · 유지보수성),
Google SWE Book(동작을 테스트, DAMP > DRY, 작은 테스트 중심), Anicel 규칙(**한 법은 가장 싼 층에서 한 번만 핀**,
「제품 코드를 끄면 빨개지는지가 증거」).

UI 에서 덧붙이는 것:

- **위젯 테스트는 넘침을 공짜로 잡는다.** 어떤 위젯 테스트든 그 크기에서 RenderFlex 넘침이 나면 실패한다. 그래서
  「크기 × 언어 × 탭」 넘침 행렬은 **위험한 조합만**: 단어가 가장 긴 표(en · fr) × 가장 좁은/낮은 화면
  (폰 세로 390 · 폰 가로 844). 한국어는 나머지 모든 위젯 테스트가 펼친다. ja · zh 는 단어가 짧다.
- **판단은 위젯 밖으로.** 「무엇을 쓸지」(대기를 파트로 걸지 컷으로 걸지, 해제인지, 빠짐/되돌리기, 마감이 어디 사는지)는
  `controllers/unit_actions.dart` 의 순수 판단 + 스토어 테스트로 핀하고, 위젯 테스트는 「누르면 그 판단이 쓰인다」
  경로 하나만 본다.
- **위젯 트리 모양은 핀하지 않는다**(「이 위젯이 있다」만 보는 테스트 금지). 예외: 차트 층 분리는 유저가 직접 요구한
  성능 법이라 페인트 횟수(`ChartPaints`)로 핀 — 화면 결과가 아니라 「무엇이 다시 그려지나」가 법이다.
- 캡처(`tool/capture`)는 게이트가 아니다 — 사람 눈으로 보는 리뷰 도구. `flutter test` 는 `test/` 만 돈다.
